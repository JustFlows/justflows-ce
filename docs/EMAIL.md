# Email delivery

## System email design and templates

Users with `email-templates:read` can inspect **Admin → Emails**. The
`email-templates:manage` capability is required to save, publish, restore, or
test a design or template. Both are separate from the `mail:read` / `mail:manage`
capabilities that govern delivery records and suppressions, so an administrator
can grant template editing per user without also exposing the mail log.

The global design controls the logo, colours, safe fallback font stack, content
width, radius, alignment, organization details, support contact, and footer.
Design and template changes remain drafts until explicitly published. Publishing
creates an immutable version; restoring creates a new draft from the built-in
safe default instead of deleting history.

Each template has a subject, hidden preheader, sanitized HTML body, and editable
plain-text companion. Previews use clearly marked synthetic values and support
desktop, mobile, and plain-text views. Test delivery only goes to the explicitly
entered address and is rate limited.

Variables use `{{variable_name}}`; optional sections use
`{{#if variable_name}}...{{/if}}`. Every template declares a typed allowlist and
representative preview values. Unknown or missing required variables block
publication. Text is escaped, URL values accept only HTTP(S) or local paths, and
action URLs are generated by the server. Templates cannot add scripts, forms,
iframes, event handlers, remote CSS, or executable code. A broken published
customization automatically falls back to its built-in template; password-reset
and other security-token rules remain outside the presentation layer.

The translation selector is populated exclusively from active languages under
**Admin → Languages**; arbitrary locale codes cannot be entered or saved. Each
template has an independently versioned draft and publication per configured
language. Locale-specific versions fall back to the site's configured default
language and then the built-in catalog. Core template keys use `core.`. Template/version identity is
stored with privacy-masked delivery diagnostics. Migration
`0022_email_templates` adds equivalent version tables for PostgreSQL, MySQL, and
MariaDB.

Plugins declare the `mail:templates` permission and call
`ctx.mail.registerTemplate(...)`. Keys must begin with the plugin manifest id;
the runtime rejects cross-plugin names and removes live registrations on
deactivation without deleting stored customizations. A definition supplies its
typed variables, safe synthetic fixture values, and built-in localized content.

Administrators configure outgoing mail under **Settings → Outgoing mail**. The
built-in transports are local sendmail and SMTP. SMTP supports no encryption,
STARTTLS, and implicit SSL/TLS. Passwords are encrypted at rest and are never
returned by the API; leaving the password field blank preserves the stored value.

The From address defaults to the administration address. Reply-To and envelope
sender are optional and independent. Use **Send test email** to see the complete
transport response. Provider credentials and message payloads are redacted from
responses, logs, and support output.

Every send creates a delivery row with a privacy-masked recipient, message type,
subject, transport, status, attempt count, timestamps, provider response, and
safe error detail. Administrators can filter the latest 200 rows and retry a
dead letter. Retry payloads are encrypted; recipient hashes support suppression
checks without exposing addresses in the log.

Non-transactional messages may opt into suppression by passing
`transactional: false` and a stable `type` to the host mail service. A
suppression can cover that type or `*`. Transactional account and security mail
is not suppressed.

## Provider plugins

A plugin declaring `mail:transport` can register an API-based provider during
activation:

```ts
ctx.mail.register({
  id: "api",
  label: "Example Mail API",
  async send(message) {
    const result = await provider.send(message);
    return { response: result.detail, messageId: result.id, status: result.status };
  },
});
```

The transport appears as `plugin:<plugin-id>.<transport-id>`. Provider plugins
should keep API keys in `ctx.secrets`, honor the configured provider limits,
and return provider response identifiers without secrets.

SPF, DKIM, and DMARC are DNS/provider controls. Justflows surfaces guidance but
does not enforce or alter DNS records.

## Sending from plugins

A plugin declaring the sensitive `mail:send` permission can send through the
host-configured transport without access to SMTP or provider credentials:

```ts
const result = await ctx.mail.send({
  to: "recipient@example.com",
  subject: "New submission",
  text: "A form was submitted.",
  replyTo: "visitor@example.com",
});
```

Plugin messages use the host delivery log, rate limits, retries, suppression
checks, and email hooks. Their delivery type is namespaced to the plugin id.
